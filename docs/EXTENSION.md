# Semester OS Connect (Chrome extension, prototype v0.1)

Folder: `extension/`. Manifest V3, no build step, no dependencies, no remote code.

## Load it (unpacked)

1. Chrome: open `chrome://extensions`, switch on **Developer mode** (top right).
2. **Load unpacked**, select the `extension` folder (`C:\Users\lucas\semesteros\extension`).
3. Pin the "Semester OS Connect" icon (puzzle icon, pin).

## Demo click path

1. In Chrome, sign in to Semester OS (https://<deployed-host-1>) and sign in to Blackboard (https://ualearn.blackboard.com) as usual, in normal tabs.
2. Click the extension icon, then **Send my classes to Semester OS** (or press the same button in the panel at the bottom right of any Blackboard Ultra page). A Blackboard course list tab opens.
3. The panel lists the current-term classes (newest term code only). Press **Open <class>**.
4. In the class, open **Schedule & Syllabus**, then the syllabus itself, wait a few seconds, press **Capture this syllabus**. (If a PDF link is on screen it is fetched as a PDF; otherwise the visible page text is captured.) Repeat per class, or **Skip class**.
5. Press **Finish and send to Semester OS**. A Semester OS tab opens, a small panel shows progress (one new class per syllabus), then it redirects to /study.

## Why guided and not fully automatic

Checked on the real UA Blackboard (read-only, no data recorded): a plain cookie-only call to the `/learn/api` memberships endpoint returned 403 (blocked), and loading `/ultra/courses/_id_1/outline` in a hidden iframe is refused by the page (no readable document). Using the page's own OAuth token was deliberately not attempted (terms-of-service and security question). So the student opens each syllabus and the extension reads what is on screen when they press Capture. It is slower but visible and consistent with the "student watches" rule.

## One-click "Scan my Blackboard" (v0.2, main path)

Click path: extension icon (or the panel on any Blackboard page) > **Scan my Blackboard**. Two background tabs open and close by themselves:
1. `/ultra/course`: `bb.js` waits for the cards and reads, per card, the identifier `<term>-<DEPT>-<NUM>-<section>` and the instructor name (`bdi` element). No clicks.
2. `/ultra/calendar`: `bb.js` does one real click on the button labelled "Due dates view" (it only switches the calendar view), waits for the list, scrolls the list up to 10 rounds until the count stops growing, and returns the page text.
3. `parse.js` (pure, tested) turns the text into deadlines: the title is the line above `Due date: M/D/YY, h:mm AM|PM (TZ) ∙ <id>: <identifier>`; date becomes ISO, time 24h, timezone abbreviation kept (CDT and CST both seen). Output is limited to the NEWEST term on the course list and to classes on that list: `{source:'blackboard', classes:[{identifier, code, section, term, title?, instructor?, assignments:[{title, dueDate, dueTime, tz}]}]}`.
4. The service worker opens `/onboarding` on the student site; `site.js` waits for the student's session, POSTs the body to `POST /courses/import` (response `{created, updated, skipped}`), and posts `window.postMessage({source:'blackboard', type:'sending'|'done'|'failed', count})` to the page. On `/onboarding` it stays there; elsewhere it redirects to /study. Progress: "Reading your courses (n)", "Reading your due dates", "Sending to Semester OS", "Done: N classes, M deadlines" (popup and panel).
5. Optional "Add a syllabus for books and grading" is the guided capture described below. The syllabus is attached to the SAME class: `site.js` calls `GET /courses` and matches `bbIdentifier`, else `courseCode`, then uses `POST /courses/{id}/materials` (PDF) or `/materials/text`; with no match it falls back to creating a class.

Verified on the real Blackboard (read-only): card selectors; instructor element; the "Due dates view" button exists (aria-label) and, after the click, the page text has the exact line shape above; the parser's regexes matched all 12 deadlines on screen (12 with identifier, 12 with a title line, timezones CDT and CST). Dry-run on synthetic text also passes (dedupe, 12 AM, newest-term filter).
NOT verified: running as an installed extension (background tab throttling, message passing), pagination beyond the visible range (the list may show only a window of dates; scrolling is best effort), `POST /courses/import` (backend being built), `bbIdentifier` in `GET /courses`, the `/onboarding` message listener timing.
Only the course list and due dates are read here. Never grades, messages or announcements.

## ONE button: "Scan my classes" (v0.4, current behaviour; supersedes the separate quick/deep buttons below)

A single run (popup or panel, plus Canvas through the same popup button): read the course list (10%), read the Due dates (25%), send classes and deadlines to `POST /courses/import` through the student site tab (40-45%, "Sending classes"), THEN, automatically, the text deep scan per class (50-95%, "Reading MIS 460 (2 of 5): page 3"), uploading one combined material per class as soon as that class is read (the site tab polls the worker with `deepNext` and posts `/courses/{id}/materials/text`, 13 s apart, 429 backoff). Final line: "Done: N classes, M pages, K skipped". One progress bar in the panel and in the popup.
- The deep part never blocks or undoes the first part: classes are already imported when it starts; if it fails, stalls or is cancelled the result is partial success (the classes stay). A class that does not load within about 30 s is skipped and counted.
- Watchdogs: every phase refreshes a heartbeat; a run with no progress for 100 s is ended with "This scan stopped responding. Try again."; opening the popup applies this immediately and shows Try again instead of a spinner. If the student site is not signed in, the run ends after 90 s with "Could not reach Semester OS. Sign in there, then try again." (the classes were not imported).
- In-page progress: a determinate bar with the percent and the current line, on the Blackboard panel and on the Semester OS page (courses 10%, due dates 25%, sending 35%, then 65% split evenly across classes and advanced as each class finishes; 100% at the end). Both pages poll the worker every second, re-render if the SPA wipes the panel, and the minimized pill shows "Semester OS NN%". The site tab's polling also keeps the run alive while uploads outlast the reading (otherwise the 100 s watchdog could end a slow upload phase).
- Class rows: as soon as the import is confirmed, the site script reads the ids from the import response (`created`/`updated`) and fills code, title and colour from `GET /courses`, and the worker keeps them. The Blackboard panel, the site panel and the popup then list each class as a row (colour dot, code, title) that opens `<site>/study/<courseId>` in a new tab while the deep scan continues; after Done there is also an "Open Semester OS" link. Links only go to the Semester OS origin; ids (8 characters, lowercase letters and digits) and colours (`#rrggbb`) are validated; no innerHTML.
- Focus and where the progress lives: the worker records the tab where the button was pressed (`origin`). That tab stays focused; the Semester OS hand-off tab and all Blackboard scan tabs are opened inactive (the one retry-in-front case returns focus to the origin tab afterwards). If the origin is a Blackboard `/ultra` or `/webapps` page, the on-page panel is forced open and expanded when the scan starts (the closed/minimized flags are reset) and shows the bar within a second, even when the button was pressed in the popup (the popup closes). If the origin is the Semester OS site itself, that tab is reloaded and does the hand-off, with its own progress panel. If the origin has no panel (for example a Canvas page or a blank tab), the bar shows on the Semester OS tab and that tab is brought to the front only at Done, together with the class rows. Known risk: Chrome may throttle timers in a tab that stays hidden for more than five minutes, which could slow the upload loop of a very long deep scan.
- Final state: when the run ends, the Blackboard panel re-opens expanded (even if it was closed or minimized) and stays until dismissed: a green check, "N classes added, M pages read, K skipped" (or "Classes added (N); page reading stopped." if the deep part failed), the clickable class rows and "Open Semester OS"; a toast at the top of the page says "Semester OS finished scanning" (or "scan stopped" on error), and the minimized pill shows a check. The worker owns the done signal (`finalizeDone`, idempotent): it fires when the site reports the last upload and also as a fallback after the reading ends once the upload queue stops draining (heartbeat older than 45 s, or 6 minutes), so a dead or throttled hand-off tab cannot leave the page without a result. An explicit Cancel clears everything and shows no result.
- Diagnostics: the panel (while running and on error), the popup and the Semester OS page show one line "Status: <phase> · Ns since last update · last error: ..." and a "Copy diagnostics" button. The copied text holds the version, phase, percent, heartbeat age, origin and tab ids, queue state, error strings and the last 40 events with ages (course list ok/failed, calendar ok/failed, hand-off tab requested, site asked for pending, site waiting for session token, site posting import, import delivered). No names, course text or tokens (course codes in the message line are masked). The Semester OS page shows "The helper has not started. Open Blackboard and press Scan my classes." after 20 s with no scan, and posts `{source:'blackboard', type:'helper'}` once a second so the page can tell the helper is installed (the onboarding page's own "Waiting for the helper" text is web code and should use that signal).
- Scan pages (REVERTED, v0.5): the Blackboard scan pages open as INACTIVE tabs in the student's current window, as in the first build that worked. A small scan window was tried and broke the scan: Blackboard Ultra switches to a narrow layout below about 1000 px, where the course cards and the "Due dates view" control differ or are missing, and unfocused small windows can be throttled. The only window fallback (if a tab cannot be created) is full size, 1280x900. If a tab renders nothing, it is brought forward for one retry and the student's previously active tab is restored. Selectors fall back to any element holding a course identifier, and the calendar control is found by aria-label or text ("Due dates").
- The Cognito session is found by scanning localStorage for `CognitoIdentityServiceProvider.<clientId>.LastAuthUser` instead of a hard-coded client id (checked on the live site: the keys exist and match config.json).
- Tab safety: the helper keeps a registry (session storage) of the tabs and the small window it created, and ONLY those are ever closed (always in `finally` blocks, via `safeRemove`: the id must be in the registry, the tab must still exist and its URL must be a Blackboard or Semester OS scan URL). It never closes, reloads, navigates or activates the student's own tabs: the course list, the calendar and the Semester OS hand-off each open in the helper's own tab inside the small window, even when the student is already on that page. Cancel, the watchdog reset, install cleanup and "clear stale run" all go through the same registry check; the helper's window and hand-off tab are closed 8 s after Done (when the student has the panel on their own page).
- Page messages from the student site script (every change, polled once a second from the worker state): `{source:'blackboard', type:'progress', percent, line, phase}`, `{type:'classes', items:[{id,code,title,color}]}`, plus the existing `sending`, `done`, `failed` and `helper`. The onboarding page can render these inline; the extension's own bar also shows on any student-site tab while a scan runs, even when it was started from Blackboard.
- Daily re-scan (default ON since v0.5, can be switched off; text "Re-scan every day: On (only new items)"): toggle in the popup and the panel's start screen; remembered in `chrome.storage.local` (`daily`), with "Last scan: <time>, N classes, M new deadlines" and "Next: <time>". Adds only the `alarms` permission. First run 24 h after the last good scan; skipped when the last good scan is under 20 h old; never more than one run per 20 h; nothing runs before the student's first scan. The quiet run reads the course list and Due dates and calls the idempotent import; the deep text part runs only for classes with no earlier upload or whose outline fingerprint (hash of the top-level item titles and count, stored locally) changed, and only for items not already hashed. A 24 h alarm plus a catch-up on browser start and every service-worker wake (if the last good scan is older than 24 h and the last attempt older than 1 h). It runs the same single scan flow quietly: no panel or toast on the student's tabs, no prompts, the small scan window opens unfocused, same tab-safety registry. If the Blackboard course list does not load, or the Semester OS tab has no session after 3 s, the run ends silently with status "needs sign-in" (shown in the popup, badge "!" on the toolbar icon until the next good scan). Deep text goes only for items not sent before (hash skipping); the 5/min and 40/day materials limits stop the upload loop gracefully; the import is idempotent so only new deadlines are added. At the end the badge shows the number of new deadlines (cleared when the popup opens or after 30 minutes). Chrome must be running for the alarm to fire; a missed day is caught up at the next start. "Scan my classes" is unchanged. - Heartbeat to the page: every student-site tab posts `{source:'blackboard', type:'progress', percent, line, phase}` EVERY second for the whole run (reading, sending, uploading, waiting), not only on change, so the page never sees silence while the worker is alive. During uploads the hand-off tab publishes a live sub-line through the worker (`siteLine`): "Uploading MIS 460 notes", "Waiting before the next upload (9 s)", "Upload limit reached, waiting (30 s)", which also refreshes the watchdog heartbeat. - Course list tolerance (v0.6): the course list scan polls every 500 ms for up to 45 s for REAL course identifiers (empty skeleton cards that already carry ids no longer count as ready; that was why a run reported "ok" after 5 s and then failed with no courses), with the same-origin REST memberships call running in parallel and retried every 10 s; up to 3 attempts per page (attempt 2 reloads the helper tab and brings it forward once, then restores the student's tab); failure reasons: "Blackboard asked you to sign in again..." (login/SSO host or path), "Blackboard is still loading...", or the generic line. Diagnostics log the host and path (no query), readyState, text length, article and course-list element counts, whether the path matches /ultra/course and which source answered ("course list via rest n=5" or "via dom"). Tabs of the current run are always closed in `finally`, even after an SSO redirect; if the student presses Scan inside a leftover helper tab, that tab is kept as theirs and the scan runs in a fresh one.
- Stale state is silent: finished or failed runs carry an `endedAt`; an error older than 30 s (site) or 10 minutes (Blackboard panel), or a result older than 30 minutes, is not rendered and `failed` is never re-posted on a plain page load; a pending import is only handed out while its run is alive (under 100 s heartbeat) and is cleared on failure. Close and Minimize are on every panel the helper injects.
- Reset helper (v0.2.0): the popup has "Reset helper" with an inline confirm ("Forget everything this helper stored?"). It clears `chrome.storage.local` and `chrome.storage.session` completely (item hashes, outline fingerprints, last-scan info, daily settings back to the default ON, run state, pending import, diagnostics, dismissal flags), clears all alarms and re-creates only the default daily alarm, clears the toolbar badge, closes only helper-created tabs, and the student-site script posts `{source:'blackboard', type:'reset', line:'Helper reset'}` (plus a `progress` message with phase `reset`) to the page; the next scan starts from zero and re-uploads everything. The same reset runs once automatically whenever the manifest version differs from the last seen one (stored in `chrome.storage.local.version`), including on first install; the manifest is now 0.2.0 so reloading the extension triggers it. Tested with the mock-chrome script (`extension/tests/test_start_path.js`, cases 8 and 9).
- No idle banners on the website: the student-site script injects NOTHING when no scan is running or just ended (the site has its own onboarding card); the extension's "not started" panel was removed. During a run (or for 30 s after it ended) the panel node is created once and only its contents change when the displayed state actually changes (no remove/re-add per tick, no flashing); hello and progress messages to the page continue.
- Idempotent injection and orphan cleanup: `site.js` and `bb.js` start with a global guard (`window.__sosSite`, `window.__sosBB`) so a second injection into the same page does nothing (one interval, one panel); each has a single named timer and posts hello/progress at a steady one per second. After the extension is reloaded, the copy still running in an already-open tab is orphaned (its extension context is gone): the new code makes such a copy stop its timer and remove its UI on the next tick, but an OLD orphan from an earlier build keeps running its old code until that tab is reloaded (F5), which is what keeps old behaviour such as the former "not started" panel flashing after an extension reload. - INDEX-FIRST deep phase (v0.3, supersedes the page-by-page reading described further down): after the classes are imported, per newest-term class one helper tab maps the outline: folders are expanded in rounds (click all closed expanders, wait until the list stops growing; depth 3, 300 items, hard 36 s in the page and 40 s in the worker), and for each item the folder path, title, type (file, document, assessment, discussion, link) and same-origin link are collected. Items are never opened and nothing is downloaded. Up to 3 classes are mapped at once. One small text material per class, titled "Blackboard content index", is uploaded with one line per item: `Folder > Subfolder > Item title [type] <https://ualearn.blackboard.com/ultra/courses/...>` (about 60 KB at most). A fingerprint of the index (hash of paths, titles and types) is stored after a successful upload; an unchanged class is skipped, a changed one is re-uploaded. The materials API has no replace-by-title (each text POST creates a new material), so the site script lists the class's materials, uploads the new index, then deletes the older "Blackboard content index" copies; if the Builder adds replace-by-title this can be dropped. Uploads are paced at 13 s apart (5 per minute limit) and the pacing waits only before the next upload, so five classes finish in roughly 1.5 to 2 minutes. Stage text: "Mapping MIS 460 (2 of 5)". Final line: "N classes added, M content items mapped".
- On-demand fetch of one item: the site posts `{source:'sos-site', type:'fetch', courseId, url}` to the page; the site script validates it (class id of 8 lowercase letters or digits, Blackboard origin and `/ultra/courses/` path only) and ALWAYS answers `{source:'blackboard', type:'fetched', courseId, ok, title, line?}`. The worker opens that single page in a helper tab (one at a time, at least 5 s apart), captures the visible text and title, and the site script uploads it as a material for that class (`/courses/{id}/materials/text`, title = the item title). Files are not read: the reply is `ok:false, line:'file: open it in Blackboard'`. Progress is posted as `progress` messages with phase `fetch`; a 28 s guard answers `ok:false` if anything stalls (the page times out at 30 s).

## Deep scan details (text only, now the second half of the single scan)

Button "Deep scan my classes" (popup and panel), with the line "Deep scan reads your course pages and sends the text you can already see to your Semester OS account." Per class of the newest term the service worker opens the course outline in a background tab, `bb.js` expands folders inline (only `aria-expanded` buttons, up to 4 rounds, 30 clicks), collects item links (skips assessments and discussions; syllabus, schedule, calendar, rubric, handout, notes, slides, reading, guide, policy names first), then opens up to 12 items per class (60 per run) one at a time and captures the visible text (pages under 120 characters, such as file viewers, are skipped and counted). All text of a class goes up as ONE combined material per class (`POST /courses/{id}/materials/text`, max 100,000 characters), because the materials API allows 5 per minute and 40 per day; the site script waits 13 s between uploads and backs off on 429 (Retry-After, 3 tries, then stops). Classes are matched through `GET /courses` (`bbIdentifier`, else course code), so run Scan my classes first. Hashes of item paths already sent are kept in `chrome.storage.local` (`deepDone`; no names or text), so a re-run skips them. Cancel scan closes the tabs; the stale-run watchdog applies. Summary: "Done: N classes, M pages, K skipped". Files (PDF, docx, pptx) are NOT read: `/ultra/courses/<id>/file/<id>` opens a viewer whose iframe points at `/bbcswebdav/...`, and a same-page `fetch`/XHR of that URL fails (the request redirects, `redirect:'manual'` returns an opaque redirect, following it fails). ## Limitations

- Blackboard terms of service on automated access are unverified; this is student-initiated, slow, read-only and visible.
- DOM fragility: selectors depend on Ultra's course card markup; the SPA needs about 8-10 seconds to render.
- Term filter: only the newest term code on the course list; older cards are ignored.
- Capture of an outline page includes unrelated page text; the backend extraction handles it as untrusted text.
- PDFs over 4 MB fall back to page text. Maximum 12 classes per run, 60,000 characters of text each.
- Desktop Chrome only; phones are not supported.

## Security model

- Host permissions only `https://ualearn.blackboard.com/*` and `https://<deployed-host-1>/*`; only permission `storage`. No `eval`, no remote code, strict extension CSP.
- Never reads, stores or sends the Blackboard password, cookies or tokens. The only Blackboard requests are same-origin GETs of a file link already visible to the student, made in the student's own tab after they press Capture.
- Nothing is read until the student presses the button; the extension never clicks, submits, enrols or changes anything on Blackboard (it only navigates the student's own tab to the course outline URL when they press Open).
- Captured data lives in `chrome.storage.session` (memory, cleared when the browser closes, and cleared after delivery). It is sent only to the student's own Semester OS account.
- The Semester OS Cognito token is read from the site's localStorage by the content script at send time, used in the Authorization header for the site's own API, and never copied into extension storage or messages.
- Captured text is untrusted: sizes capped, shown only with `textContent` (never HTML), sent as plain text to the API, which already treats syllabus text as untrusted data.
- Background messages are checked by sender origin (Blackboard, site, or the popup).
